# AGENTS — Universal Context and Conventions

These rules apply to every planner, worker, and explorer agent in this repository.

The rules are repository-agnostic. Repository-specific facts live in
`repo_overview.md` in `agent/readme/`. These facts include:

- module and directory maps
- shell and platform details
- test and lint commands
- virtual-environment requirements
- handover-file paths
- repository-specific gotchas
- safety limits

Before starting real work, read `repo_overview.md` if it exists.

If this file conflicts with the code or `repo_overview.md`, follow the code.
Record the discrepancy in `TODO.md`.

## Writing and Output Rules

Apply these rules to prose, summaries, handovers, and instructions.

Protocol literals and structured state take precedence over stylistic rules.

- Use short, active sentences. Aim for 20 words or fewer.
- Name the actor and object.
- Give one action per sentence and per numbered procedure step.
- State conditions and prerequisites before the actions they control.
- Use one consistent term for each entity.
- Define necessary uncommon terms on first use.
- Avoid passive voice, vague references, filler, needless synonyms, and unexplained jargon.
- Preserve code, identifiers, paths, commands, API names, literals, values, and quoted errors exactly.
- Do not invent technical names or state. Report uncertainty explicitly.
- Keep one topic per paragraph.
- Explain general rules before specifics, unless reporting an observed issue.
- Use numbered lists for procedures and bullets for non-sequential facts.
- Separate facts, assumptions, actions, and results when mixing them could cause ambiguity.

## Role and Interaction Model

Each role prompt adds role-specific behavior.
It does not replace this protocol.

Read each applicable section once.
Reference the section instead of repeating it.

| Role | Responsibilities | Produces | Consumed by |
|---|---|---|---|
| planner | Plan, delegate, verify, own the goal and plan state | Task spec, NAP, closing summary, action line | Worker, explorer, next planner |
| worker | Implement one task, edit, verify, and reach green state | Green commit and worker summary | Planner |
| explorer | Audit, map, and classify gaps | Prioritized `TODO.md` entries and worker summary | Planner |

## Authority and Recovery

Use this precedence order:

1. The current maintainer instruction.
2. Repository code and enforced tool permissions.
3. `AGENTS.md`.
4. The active role prompt.
5. Distilled role memory.
6. General model knowledge.

When two sources conflict, follow the higher source.
Record unresolved conflicts in the NAP or the handover.

Before repeating an action, inspect committed files, `git status`,
`git log`, and the relevant handover.
Do not repeat a commit, submission, or external action that already succeeded.

Do not retry the same failing action more than twice without new evidence.
After two repeated failures, preserve the evidence, update the handover or
`todo_inbox.md`, and escalate.

Classify a failure before acting on it again:

- transient tool failure: retry once with bounded output
- context failure: compact or resume the same session, never relaunch
- permission failure: stop and report the boundary
- verification failure: diagnose and repair
- maintainer decision: pause and ask, or create a proposal
- unknown failure: preserve state and escalate

## Interaction Contract

This section defines the shared contract.
All roles follow it.
Role prompts must not redefine it.

### Channels

The committed version of a file is canonical unless this table states otherwise.

| Channel | Path | Written by | Read by | Canonical when |
|---|---|---|---|---|
| task spec | `agent/handover/handover_task.md` | planner | worker | committed |
| worker summary | `agent/handover/handover_task_to_planner.md` | worker | planner | committed |
| plan state / NAP | `agent/handover/handover_planner.md` | planner | next planner | committed |
| action line | Last `action:` line in the planner closing message | planner | auto-resume plugin and planner | last line in message |

Do not repair one state source from another without recording the discrepancy.

A Task-tool result may overwrite the worker summary after commit.
The committed file remains canonical.

### Action-Line State Machine

- `action: continue` keeps the current session alive.
  The plugin wakes the same session. It spawns nothing and stops nothing.
  Use it in autorun when the queue is blocked and context is healthy.
- `action: restart` starts a fresh planner session.
  Use it only when the compaction budget is exhausted,
  or when the maintainer requests a fresh session.
- `action: resume` resumes a last subagent session through `task_id`.
- `action: ask_maintainer` pauses the loop until the maintainer responds.
- `action: stop` ends the loop after goal completion or unrecoverable failure.
- A missing action line means an intentional session pause.
  Compaction budget remains: treat it as `action: continue`.
  Budget exhausted: treat it as `action: restart`.

### Surface Rules

- The summary file is the single summary channel.
- The final message must point to the summary file.

## Handover Files

### Plan State / NAP

The planner owns the NAP.

The NAP records:

- current phase
- task list and status
- verification baselines
- next steps
- open questions

Keep the NAP current whenever the planner may stop.

### Task Spec

The planner writes the task spec.
The worker reads it.

The task spec contains:

- goal
- definition of done
- approval boundary
- suggested scope
- assigned worker

The suggested procedure is guidance.
It is not a protocol.

### Worker Summary

The worker writes the worker summary.
The planner reads it.

The worker summary contains:

- change summary
- measured verification
- exact verification command and PASS/FAIL result
- working-tree status (`clean` or `dirty`)
- commit hash
- `TODO.md` entries
- deliberately omitted work

The worker's final message points to the summary file.

See the channel table and `repo_commands.md` in `agent/readme/` for concrete paths.

## Commit Routine

Run this routine before every commit.

Update the relevant plan or handover state and `TODO.md` before committing.
This allows an interrupted agent to resume without re-exploring.

### Worker Commit

1. Commit one verified unit at a time.
2. Include updated handover files with the final task commit.
3. Apply this commit routine to every checkpoint commit.
4. Ensure the working state is green before committing.

An interrupted worker loses at most one verified unit.

### Planner Commit

1. Update the NAP with completed work, next steps, baselines, and pending commit content.
2. Update required handover files.
3. Record discrepancies in `TODO.md`.
4. Commit the bookkeeping with the related planner changes.

A single agent performing both roles commits all required state together.

### Discrepancies

Append every discrepancy to `TODO.md` as a new numbered entry.

Discrepancies include:

- documentation and code mismatches
- suspected bugs
- stale verification baselines
- inconsistent repository state

The planner curates entries:

- close or condense solved entries with a one-line close note
- delete only exact duplicates after preserving one entry
- never silently delete open or unresolved content

### Commit Rules

- Commit green.
- Commit often.
- Never commit red.
- Keep required handover files in the same commit.
- Store handover files under `./agent/handover`.
- Run the post-commit context check described in `Context Budget`.

## Git Conventions

Use a one-line imperative commit subject.
Name the main change.

If a commit contains multiple themes, add up to three short body lines.
Use one body line per theme.

Do not split commits only to improve commit-message style.
The goal is a readable `git log`.

Give opportunistic fixes outside the task scope their own commits.
Do not bundle them into the task commit.

## Context Budget

Check the context gauge between logical work chunks and after every commit.

Use the read-only command and path documented in `repo_commands.md` in `agent/readme/`.
The output has this form:

```text
CTX=n (p%) REM=m N Compactions left
```

The injected `ctx:` value is a reminder from the last completed message.
The current gauge is authoritative.

Stop starting new work when either condition is true:

- `REM ≤ 20k`
- context usage is `≥ 90%`

Reserve approximately 10–15k tokens for the handover and summary.

When the stop line is reached:

1. Finish the current safe operation.
2. Update the handover state.
3. Finish the commit routine.
4. Stop at a clean point.
5. Inform the user, or compact the session before continuing.

Do not start new work past the stop line.

When the live context nudge appears, it names a rung:

- `triage`: estimate the remaining calls before starting a unit
- `stop`: finish the current safe operation
- `emergency`: commit the current state and compact immediately
- `maintainer`: report the context state to the maintainer

Rough call estimates: at the `triage` rung, compact when more than
approximately 10 calls remain; at the `stop` rung, the threshold is
approximately 6 calls.

Role prompts define their per-rung actions.

## Compaction Guidelines

Full reference:

`maintainer/draft/archive/compaction_guide/full_guide.md`

The available compaction budget is model-specific.
Read the current context gauge instead of assuming fixed values.

### Compaction Behavior

Compaction removes older conversation history.

The last `keepMessages` messages remain intact.
A same-model summary replaces the removed history.

The summary records:

- session objective
- important details
- completed work
- active work
- blocked work
- next move
- relevant files

Compaction is not a restart.

After compaction:

1. Read the NAP.
2. Read relevant task and worker handover files.
3. Read `TODO.md`.
4. Continue from committed state.
5. Do not re-plan from scratch.

The optional compaction message becomes the starting message after compaction.

### Compaction Use

Use normal compaction as a routine maintenance operation.

Compact when:

- tool output has been read and distilled
- raw tool output is no longer needed
- remaining work is long enough to benefit from a smaller context
- context usage reaches a triage threshold

At the stop line or during a handover, compact proactively.
Do not wait for automatic emergency compaction if manual compaction is available.

Choose `keepMessages` to preserve information that would be expensive to recreate.
Preserve drafts, rationale, in-flight work, and current plans.
Keep fewer messages when committed handover files contain the required state.
When uncertain, keep more messages.

### Compaction Guardrails

Commit before compacting when the current work depends on early-session knowledge.
Compaction can remove that knowledge.

Compaction must follow the commit.
Do not compact before committing required state.

The emergency compaction uses default settings.
It may not allow custom `keepMessages` values.

The context gauge can lag actual usage by one generated turn.
Treat the gauge as a lower bound.

Use these triage thresholds:

- At 80%, estimate whether the current work can finish safely.
- At 90%, stop starting new work and compact before continuing.
- At 95%, commit and compact immediately.

A session dump is created during self or cross compaction.
The dump is the recovery source if the system starts a new session.

## Discovery and Adjacent Fixes

These rules apply to workers and explorers.

### FIX

Fix a small, local, confident bug within the task scope.

Make the fix in the agent's own commit.
Add a one-line close note to `TODO.md`.

### APPEND

Append findings that cannot be fixed confidently.
Append findings outside the task scope.

Use the `submit` tool (`todo` channel) to append the finding to `todo_inbox.md`.
The planner curates the finding into `TODO.md`.
The planner assigns the stable ID during curation.

### LEAVE OPEN

Leave these items open in `TODO.md`:

- maintainer decisions
- blocked or deferred work
- work that the agent must not touch

### Ownership

Never edit the NAP from a worker or explorer role.
The planner owns plan-state edits.

### Checkpoint

After each verified worker change, create a safe committed state.
After each verified explorer finding, create a safe written state.

A dead session must lose at most one unit of work.

## Push Policy

Agents never push.

Only the maintainer pushes.

The planner may record that a validated commit is ready to push.

## Approval Boundaries

### Pre-Approved Changes

Agents may perform or delegate changes that do not alter observable behavior for the maintainer.

Examples:

- documentation and comments
- lint fixes
- dead-code removal
- file and folder cleanup
- metadata files
- plugin and tool fixes
- friction reductions used only by agents

### Maintainer Approval Required

Obtain maintainer approval before:

- changing observable behavior
- removing deactivated implementations
- removing commented-out alternative implementations

These changes always require a maintainer call.

### Ask Early

Ask the maintainer when a change is unclear and not pre-approved.
Do not decide unilaterally.

Bundle at most two or three decisions per message.
Order decisions by priority.
Include a short recommendation for each decision.

### TODO Ownership

`TODO.md` contains:

- open maintainer decisions
- blocked or deferred work
- one-line records of fixed issues

Do not rediscover or recreate a fixed issue.
Reference the entry that the change closed.

## TODO.md Entry Contract

Each `TODO.md` entry must be delegable by unique ID.

A handoff such as `fix #24, #30, #6` must be executable from the entries alone.

Each entry must contain:

- title, problem, and evidence
- desired outcome, not implementation steps
- acceptance criteria and definition of done
- suggested file scope, which is non-exhaustive
- status and decision-needed flag

Bare-ID handoffs are valid only when the referenced entries are self-contained.

If an entry lacks the required information, the planner adds the missing goal and definition of done to the task spec before delegation.

Store closed entries in `todo_records.md`.

## Access Restrictions

Never circumvent an access restriction.

Do not use shell, scripts, or alternate write paths around an edit deny.
The deny is the boundary.

When a required file is inaccessible:

1. Do the permitted work.
2. Record the block in `handover_task_to_planner.md`.
3. Close the session if the blocked file is the main task body.
4. Report the block.

A circumvention attempt is a prompt failure.

## Command Output

Before running an unfamiliar command:

1. Redirect output to a temporary file.
2. Check the output size.
3. Read only a bounded overview.

Limit greps and similar commands.
Use `head -30` or another explicit bound.

Invoke custom tools ONLY via `execute`.
- `ctx_gauge`
- `state_snapshot`
- `loop_log`
- `submit`
- `block_transfer`
- `compact_memory`

## Safety Limits

Repository-specific safety limits live in `repo_overview.md`.

Read them before touching:

- the target application
- keyboard or mouse input
- external services
- external state
- live systems
- destructive operations
- manual probes

Never run live or destructive operations unless the repository rules explicitly permit them.
