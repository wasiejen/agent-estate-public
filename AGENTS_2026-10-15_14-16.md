# AGENTS — universal context & conventions

These rules apply to every agent (planner or worker) in this repo.
They are stable and repo-agnostic.

Repo-specific facts — module map, shell, platform, test and lint commands,
venv, handover paths, gotchas — live in `repo_overview.md`
(folder: `agent/readme/`).

Before real work, read `repo_overview.md` if it exists.
It is the repo map. Read it first.

If a rule here conflicts with the code or `repo_overview.md`,
the code wins. Flag the discrepancy in `TODO.md`.

---

## Role & interaction model

Each role has a prompt. The prompt adds role-specific behavior on top
of this shared protocol. It does not replace the protocol.
Read each section once. Reference it by name.

| Role | Verb | Produces | Consumed by |
|---|---|---|---|
| planner | plan, delegate, verify, own goal + plan state | task spec, NAP, closing summary + action line | workers, next planner session |
| worker | implement one task, edit → verify → green | a green commit + `handover_task_to_planner.md` | planner |
| explorer | audit + map, classify gaps | prioritized `TODO.md` entries + `handover_task_to_planner.md` | planner |

## Interaction contract

This section defines the contract once. All roles read it.
Do not restate it in role prompts.

### Channels

The committed version of a file is canonical unless noted below.

| Channel | Path | Written by | Read by | Canonical when |
|---|---|---|---|---|
| task spec | `agent/handover/handover_task.md` | planner | worker | committed |
| worker summary | `agent/handover/handover_task_to_planner.md` | worker | planner | committed (the Task-tool result may clobber it post-commit — the committed copy wins) |
| plan state / NAP | `agent/handover/handover_planner.md` | planner | planner (next session) | committed |
| action line | last `action:` line of planner's closing message | planner | auto-resume plugin / planner | last one in the message |
| maintainer → role | `maintainer/inbox_<role>/` | maintainer | named role | moved to `maintainer/done/` after handling |

### Action-line state machine

The planner reads these states from its closing message.

- `action: restart` — start a fresh planner session. Default.
  If the line is missing or unclear, treat it as `restart`.
- `action: resume` — resume the last sub-agent session via `task_id`.
  Do not re-inject the task.
- `action: ask_maintainer` — pause the loop. Wait for the maintainer's answer.
- `action: stop` — goal reached or unrecoverable state
  (compaction budget fully exhausted).

In autorun, an IDLE session (nothing actionable remaining) is not a stop.
The agent performs the maintenance scope (its orientation's idle lane)
and closes with `action: restart`.
The agent is always active in some form.
`stop` in autorun is reserved for unrecoverable states
or direct maintainer interaction.

### Surface rules

- The summary file is the single summary channel.
  An agent's final message is a short pointer (path),
  never a re-dump of the summary.
- The worker never touches the NAP.
- The planner never performs a worker's implementation.
- Committed state is the resume contract.
  A fresh session rebuilds reality from files and `git log`,
  never from memory.

## Handover files

- **NAP** (planner-owned): phase, task list + status, baselines,
  next steps, open questions. Keep it current at every moment
  the planner may stop.
- **Task spec** (planner writes, worker reads): goal + definition of done
  + approval boundary + suggested scope + assigned worker.
  Procedure is a suggestion, not a protocol.
- **Worker summary** (worker writes, planner reads): executive summary
  of what changed, measured verification, commit hash, `TODO.md` entries,
  what was deliberately not done.
  The worker's final message is a short pointer to it.

Concrete paths: see the channels table above and `repo_overview.md`.

## Commit routine

Update plan/handover state and `TODO.md` **before** committing.
An interrupted agent resumes from committed state
without re-exploring.

Two-party split:

1. The worker commits code in checkpoint commits — one per verified unit.
   An interrupted session loses at most one unit.
   `TODO.md` + the task's handover files ride the **final** commit.
   The commit routine still applies to each intermediate commit:
   update plan state before committing, append discrepancies.
2. The planner updates the NAP (what is done, next, baselines,
   what is about to be committed) and commits it with its bookkeeping.
   A single agent doing both roles commits everything in one commit.
3. Append every discrepancy to `TODO.md` as a new numbered entry.
   Discrepancies include: doc/code mismatches, suspected bugs,
   stale baselines.
   Append new entries. The planner curates:
   close or condense solved items with a one-line close note,
   delete only exact duplicates (preserve the surviving entry),
   never silently delete open or unresolved content.
4. Run the post-commit context check. See Compaction Guidelines.

Rules:

- Commit green. Commit often. Never commit red.
- Handover files ride along in the same commit.
- Handover files live in `./agent/handover`.

## Push policy

Agents never push. Only the maintainer pushes.
The planner may note in its summary when a validated chunk
is committed and ready to push.

## Discovery & adjacent fixes

Shared by worker and explorer.

- **FIX** — a small, local, confident bug inside the task scope.
  Fix it in your own commit. Add a one-line `TODO.md` close note.
- **APPEND** — a finding you cannot confidently fix
  or that is out of scope.
  Append it to `todo_inbox.md` via the `submit.todo` tool.
  The planner curates it into `TODO.md` and assigns the stable ID.
- **LEAVE OPEN** in `TODO.md` — maintainer calls, blocked/deferred work,
  items you must not touch.
- **Never touch the NAP** from a worker or explorer role.
  Plan-state edits belong to the planner.
- **Checkpoint each unit.** After each verified change (worker)
  or each verified finding (explorer), write it to a safe
  committed state. A dead session loses at most one unit.

## Approval boundaries

- **Pre-approved** (do or delegate; no maintainer call):
  changes that do not alter observable behavior for the maintainer.
  Examples: docs/comments, lint fixes, dead-code removal,
  file/folder cleanup, meta files, plugin/tool fixes,
  friction removals used only by agents.
- **Needs maintainer approval:**
  any observable behavior change, and removal of
  deactivated or commented-out alternative implementations.
  These always require a maintainer call.
- **Ask early** — if something is unclear and not pre-approved,
  ask the maintainer. Do not decide unilaterally.
  Bundle decisions: at most 2–3 items per message.
  Order each item by priority. Include a short recommendation.
- `TODO.md` holds open items (maintainer calls, blocked/deferred work)
  plus one-line records of fixed issues.
  Never re-derive a fixed item. Flag the entry it closed.

## `TODO.md` entry contract

A `TODO.md` entry must be self-contained enough to delegate
by unique ID. A handoff like "fix #24, #30, #6" must be
executable from the entry alone.

Minimum fields:

- title / problem + evidence
- desired outcome (goal, not steps)
- acceptance criteria (definition of done)
- suggested scope (files — non-exhaustive)
- status / decision-needed flag

Bare-ID handoffs are allowed only when the referenced entries
are self-contained. Otherwise, the planner enriches the task spec
with the missing goal + definition of done before delegating.

Closed entries live in `todo_records.md`.

## Git conventions

- Commit message: one-line imperative subject naming the main change.
  If the commit covers more than one theme, add up to ~3 short
  body lines, one per theme.
  Multi-theme commits are fine.
  Never split commits just for message style.
  Goal: `git log` reads as a small work summary on its own.
- Opportunistic fixes made outside a task's scope get their own
  commit(s) with clear subjects.
  Do not bundle them into the task commit
  just because multi-theme is allowed.

## Compaction Guidelines

Full reference: `maintainer/draft/compaction_guide/full_guide.md`.
Numbers below are current for the planner model (170k window)
on this host. Mechanics apply to every agent.
Numbers are per model.
Check your ctx: the inline message shows `#n compactions left`.

### What compaction is

Compaction trims old history.
The last `keepMessages` messages stay intact (tool calls + outputs).
A same-model summary of the whole session replaces the dropped part.

The summary records: session objective, important details,
work state (completed, active, blocked), next move, relevant files.

Compaction is not a restart.
After compaction, re-read your head files (NAP, handover/task files,
`TODO.md`) and continue.
Never re-plan from scratch.

The optional `Message` content delivers to your compacted self
as the starting message.

# Write clear, precise technical prose.

- Use short, active sentences (20 words or fewer). Name the actor and object.
- Give one action per sentence. Give one action per numbered procedure step.
- State conditions and prerequisites before the action they control.
- Use one consistent term for each entity. Define necessary uncommon terms on first use.
- Avoid passive voice, vague pronouns, filler, needless synonyms, and unexplained jargon.
- Preserve code, identifiers, paths, commands, API names, literals, and quoted errors exactly.
- Do not invent technical names. State uncertainty explicitly.
- Keep one topic per paragraph. Explain the general case before specifics, unless reporting an observed issue.
- Use numbered lists for procedures and bullet lists for non-sequential facts.
- Separate facts, assumptions, actions, and results into distinct sections.
